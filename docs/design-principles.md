AUI는 사용자가 행동을 이해하고, AI가 같은 규칙으로 화면을 조합하도록 만든다. 프로젝트의 개성은 Theme에서 표현하고, 컴포넌트는 예측 가능한 외형과 동작을 제공한다.

## 1. 행동의 중요도가 보인다

primary는 주요 행동, secondary는 보조 행동, ghost는 낮은 강조, destructive는 위험한 행동을 표현한다. 한 영역의 주요 행동은 하나다. variant를 나란히 비교할 수 있어야 하며, 색만으로 위험이나 상태를 알리지 않는다. 실제 사용 흐름에서는 같은 영역의 여러 버튼이 모두 주요 행동처럼 경쟁하지 않게 한다.

Toggle·ToggleGroup·Select·Sidebar의 선택·현재 위치는 brand 스케일의 연한 단계(brand-a3 배경, brand-12 글자)를 쓰고 Tabs는 primary 밑줄로 표시한다. 선택은 지속되는 상태이므로 주요 실행과 같은 채운 배경을 쓰지 않는다. hover·키보드 탐색은 accent(neutral-a4), Checkbox·RadioGroup·Switch의 켜짐과 진행량은 primary, 오류·위험은 danger 스케일로 구분한다. 완료·주의·안내는 success·warning·info 스케일의 soft 표현을 쓴다. 이미 선택된 항목은 hover 중에도 표시가 남아야 한다.

## 2. 같은 역할은 같은 규칙을 쓴다

색·font·typography·radius·밀도는 가까운 Theme를 따른다. 색은 brand·neutral·danger·success·warning·info 12단계 스케일의 단계 번호로 고르고, radius는 역할별 단계(배지 1, 작은 컨트롤 2, 버튼·입력 3, 카드 4, 모달 5)에 Theme 배율을 곱한다. 간격·치수·motion은 패키지의 공통 기준에 Theme scaling을 곱한다. Input과 Select의 md·sm 높이, 컨트롤의 포커스·오류 표시처럼 사용자가 같은 의미로 받아들이는 요소는 맞춘다. 개별 화면의 임의 CSS 대신 Theme 또는 공개 API를 고친다.

배경에 맞는 전경색을 함께 사용한다. card에는 cardForeground, popover에는 popoverForeground를 연결하고 기본 Text·투명한 컨트롤은 현재 표면의 글자색을 물려받는다. muted·field의 주된 글자는 foreground, 설명은 mutedForeground를 사용한다. 기본 preset에서 색이 같더라도 역할이 다른 token을 대신 쓰지 않는다. 배경과 전경을 서로 다르게 주입한 Theme로도 확인한다.

원형 아바타·thumb, pill 형태, 화면 가장자리에 붙는 Drawer는 형태상 예외다. 그 외 작은 표면도 radius=0이면 각진다. 서비스의 도메인 색과 타입은 공통 패키지에 넣지 않는다.

## 3. 상태를 눈과 조작으로 확인할 수 있다

상호작용에는 해당되는 hover·pressed·focus-visible·disabled·loading·selected·invalid 상태를 제공한다. 포커스는 배경과 구분되고 잘리지 않아야 한다. Button·ButtonLink·IconButton의 포커스는 Theme의 foreground 색으로 테두리와 이어지는 한 줄로 표시하며 바깥쪽에 간격을 두지 않는다. 오류는 설명과 컨트롤 표시를 함께 연결한다. 처리 중에는 진행 상황을 알리고 중복 실행을 막는다.

Input·Textarea·Select·Toggle·Tabs 등의 포커스 선은 기존 테두리에 겹쳐 한 줄로 표시한다. Checkbox·RadioGroup·Switch·Slider는 보이지 않는 클릭 영역 주위에 별도 선을 그리지 않고 실제 표시 부분만 강조한다. 클릭 영역의 크기는 유지하며, 오류 상태에서는 포커스에도 destructive 색을 사용한다.

## 4. 내용이 길어져도 의미가 남는다

짧은 예제만으로 완성을 판단하지 않는다. 긴 한글·영문, 여러 줄 label과 오류, 좁은 화면에서도 버튼·아이콘·입력·footer가 경계를 지킨다. 긴 표는 표 영역에서 스크롤하고, 화면 전체가 옆으로 밀리지 않게 한다. 화면을 가리는 대신 내용을 다시 읽을 방법을 제공한다.

## 5. 입력 방식과 화면 크기에 의존하지 않는다

키보드·터치·포인터를 지원하며 필수 안내를 hover에만 두지 않는다. 터치 컨트롤은 최소 44×44 CSS px을 프로젝트 기준으로 삼고 입력 글자는 최소 16px을 유지한다. 320·390px과 넓은 화면, 글자 확대에서 확인한다. 모바일 브라우저 검사와 실제 Capacitor 기기 검사는 구분해서 기록한다.

## 6. 색과 움직임은 정보 전달을 돕는다

기본 Theme의 일반 텍스트 대비는 4.5:1을 확인하고, 컨트롤을 식별하는 데 필요한 경계·상태는 인접 색과 3:1을 확인한다. WCAG의 큰 글자·비활성 등 적용 조건을 구분한다. 색 변경 시 글자·배경 쌍과 Portal도 함께 본다.

움직임은 열림·닫힘·선택의 변화를 설명한다. 닫힐 때도 자연스럽게 끝나고 포커스가 돌아와야 한다. reduced motion에서는 이동과 반복 움직임을 줄인다. 스킬의 특정 폰트·팔레트·숫자는 제품에 맞는 근거 없이 강제하지 않는다.

## 7. Story는 디자인을 선택하고 검수하는 도구다

기본 예제와 Controls에 더해 variant·크기·주요 상태·사용 흐름 중 필요한 예제를 남긴다. 같은 목적의 비교는 묶되 Story 개수를 일률적으로 제한하지 않는다. 테스트 전용 장치만 숨기고 오류·로딩·비활성 같은 사용 상태는 공개한다. 예제의 저장·취소·선택 버튼은 실행 결과를 보여준다.

## 8. 완료는 실제 화면과 동작으로 판단한다

변경한 컴포넌트를 두 Theme의 라이트·다크와 모바일·웹에서 확인한다. 검사 결과에는 Story, 조건, 관찰한 문제, 수정, 재확인한 범위를 남긴다. 자동 테스트 통과와 시각 검토를 구분하고 실행하지 않은 검사는 완료로 표시하지 않는다.

이 원칙은 [수집한 UI/UX 스킬과 공식 가이드](design-review-references.md)를 AUI에 맞게 적용한 것이다. 접근성 수치·예외는 해당 문서의 W3C 원문을 기준으로 판단한다. 44px은 AUI의 터치 정책이며 WCAG AA의 최소 수치라는 뜻은 아니다.
